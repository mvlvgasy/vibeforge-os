# Frame 14 — Agent delivery architecture

> **Fundamental** operational frame: materializes the decision of **how to deliver** a project
> that includes an AI agent component. It enforces structured consideration of the agent
> delivery architecture options instead of defaulting to one pattern out of habit.

## Problem solved

Without this frame, projects with an agent component tend to be delivered **by default** in the "deterministic custom app" pattern (scripts + workflows + occasional LLM calls). This choice is rarely explicitly **compared** to the other options available on the market:

- **Hosted managed agents** — cloud multi-agent with a native memory store + consolidation
- **Self-hosted multi-agent runtime** — open source, multi-model, native dashboard
- **Pure custom app** — without LLM, just deterministic workflows (degenerate case)

Typical failure mode:
- A high-stakes flow framed as pattern A by default. Often the **correct** decision when cost-of-failure is unbounded, **but the comparison is not explicit** in the PRD = weak methodological signal.
- Risk for future projects: systematically making the same choice out of habit, OR adopting a new technology by hype without fit.

## Solution — Mandatory explicit framing

Any Vibeforge project with an agent component MUST, in Phase 1 Framing of the project workflow (doctrine 12), explicitly document:

1. **Which delivery architecture pattern is selected** (A, B, C or D — cf. § The 4 patterns)
2. **Why the 3 others were rejected** in the form of a comparative table (5 criteria)
3. **External integration pattern** per connected service (direct API / MCP Tunnel / CLI wrapper)

The `business-analyst` discovers the criteria. The `architecte` synthesizes the comparative table in the PRD. The `reviewer-prd` verifies in Phase 2.

## Pattern 0 — Prerequisite: mature OSS covering 80%+ already exists?

**Before** evaluating the 4 patterns below, **mandatory checklist**:

> *"Is there a mature OSS (MIT/Apache/equivalent) that covers 80%+ of the project's runtime/framework need?"*

### If yes → compose on top of it, do not reimplement

Composing on a mature OSS runtime instead of reimplementing it can save months of R&D. Recurring industrial pattern: Vercel on Next.js, Supabase on Postgres.

Concrete action:
- The architecte audits the candidate OSS (code review, maturity check, license, extension points)
- If the audit is positive: the chosen integration pattern = "compose on top" + identification of the 3 extension paths (REST API / MCP / native plugin)
- If the audit is negative (blocking architecture, abandoned project, etc.): move down to the 4 patterns A/B/C/D

### If no, or borderline case 60-80% coverage

Continue normal framing toward the 4 patterns A/B/C/D below. Evaluate the cost-benefit of a partial OSS fork vs build from scratch.

### Anti-patterns to avoid

- **Engineer's ego**: "we can do better ourselves" — often true technically, false economically
- **Excessive vendor-lock fear**: an MIT OSS is NOT a vendor-lock (you can fork at any time)
- **Underestimating OSS maturity**: a v0.14 project with ~90 core files is often more mature than 3 months of solo R&D

### Reference

Record the strategic justification and the industrial examples matrix in `registers/learnings.md` when you make a compose-vs-build decision.

## The 4 agent delivery architecture patterns

### Pattern A — Deterministic custom app (+ occasional LLM as assist)

```
┌─ Frontend (Next.js, Vue, Svelte, whatever)
├─ Custom backend (Python, Node, Go) — deterministic scripts + workflows
├─ Application DB (Postgres, MongoDB)
├─ Occasional LLM via direct API (Anthropic Messages, Mistral, OpenAI compatible)
│  └─ No autonomous agent, just structured LLM calls
└─ Hosting: your choice (Vercel, Hetzner, client on-prem)
```

**When to use it**:
- **Predictable** business logic (clear workflows, low ambiguity)
- **Unbounded cost-of-failure** (financial, medical, legal, security flows)
- Deterministic control preferred over agent flexibility
- Critical data sovereignty (can use Mistral EU)
- Ongoing costs to minimize

**Typical example**: an accounts-receivable / finance assistant. Mail tickets, drafts generated by occasional LLM calls, accounting/payment actions via direct APIs, human validation by an operator on every irreversible action.

**Estimated dev effort**: 3-4 weeks for an MVP of that complexity (60-70% of the time = custom deterministic scripts).

### Pattern B — Custom UI + hosted managed-agents backend

```
┌─ Frontend (custom, by you)
├─ Lightweight backend (Next.js API routes) — dispatch to the hosted runtime
├─ → Hosted managed agents
│     ├─ Defined agents (system prompts + tools + MCP)
│     ├─ Hosted memory store
│     ├─ Native consolidation
│     └─ Sub-agents orchestration
└─ → MCP servers (internal or public) via tunnels or API
```

**When to use it**:
- **Genuine dynamic multi-agent need** (5+ agents that talk to each other, dispatch, share memory)
- **Zero runtime infra on your side** (the provider handles it)
- Critical dev speed (a hosted runtime ≈ 40-50% faster to deliver than an equivalent pattern A)
- Acceptable ongoing token costs
- Acceptable provider vendor-lock (partial data sovereignty)
- **Bounded** cost-of-failure (the agent can hallucinate but the damage is recoverable)

**Typical example**: a small-business assistant — reservations by mail+WhatsApp, stock management via an internal POS, review responses with owner validation on negatives. 5-6 orchestrated agents, an owner dashboard app, low cost-of-failure (a missed auto-reservation is correctable, no PII leak).

**Estimated dev effort**: 1.5-2 weeks for an MVP equivalent to the previous one (40-50% saving over pattern A thanks to delegating orchestration to the provider).

### Pattern C — Custom UI + self-hosted multi-agent runtime backend

```
┌─ Frontend (custom, by you)
├─ Lightweight backend — dispatch to the self-hosted runtime
├─ → Self-hosted multi-agent runtime (on your infra or the client's)
│     ├─ Open source multi-agent runtime
│     ├─ Native multi-agent dashboard
│     ├─ Multi-model (mix providers as needed)
│     └─ You host + scale + maintain
└─ → APIs / MCP servers
```

**When to use it**:
- Multi-agent + **total data sovereignty** required (banking, healthcare, gov)
- **Multi-model** desired (mix a strong model for judgement, a cheap self-hosted one for bulk, an EU model for compliance)
- No vendor-lock acceptable
- You (or your client) have an ops team to manage the runtime infra
- High agent volume (a fixed-cost server is fast ROI vs per-token hosted costs)

**Typical example**: a sensitive internal project where data sovereignty is valued + a real multi-agent need. OR a banking/healthcare client where compliance forbids sending data to a third-party cloud.

**Estimated dev effort**: 2-3 weeks (~same as B, slightly more due to the self-host setup).

### Pattern D — Pure custom app (without LLM)

```
┌─ Frontend
├─ Custom backend — pure deterministic workflows
├─ DB
└─ No LLM at all
```

**When to use it**:
- Degenerate case: the project does not really need AI
- The AI agent was a nice-to-have, but the ROI does not justify the integration effort
- The LLM cost is too high for the usage volume

**Typical example**: a simple analytics dashboard, a lightweight CRM, a stock management tool without recommendations.

**Estimated dev effort**: variable by scope, but often simpler with no LLM to manage.

## Quick decision matrix

| Decisive criterion | A deterministic custom | B hosted managed | C self-hosted runtime | D pure custom |
|---|---|---|---|---|
| **Cost-of-failure** | **Unbounded** | Bounded | Bounded | N/A |
| **Dev speed** | Slow (3-4 wk) | **Fast (1.5-2 wk)** | Moderate (2-3 wk) | Variable |
| **Vendor-lock** | **None** | Total (provider) | **None (OSS)** | **None** |
| **Ongoing costs** | **Low** | Per-token (variable) | Fixed compute | **Trivial** |
| **Data sovereignty** | **Total (EU model)** | Partial | **Total** | **Total** |
| **Multi-model** | Possible (swap provider) | Single provider | **Native** | N/A |
| **Visual observability** | Custom dev (heavy) | Provider console | **Native dashboard** | N/A |
| **Agent memory / learning** | To code custom | **Native (memory store + consolidation)** | To code or plugin | N/A |
| **Initial learning effort** | You already master it | ~3-5 day curve | ~1 week setup | Low |

## Recommendations by client profile

| Client context | Recommended pattern |
|---|---|
| **Regulated banking / fintech** | **A** + EU model or self-hosted open weight |
| **Healthcare / medical strict GDPR** | **A** + EU or on-prem open weight model |
| **Gov / defense / sovereignty** | **A** + open weight on sovereign cloud |
| **Restaurant / SMB / e-commerce / SMB SaaS** | **B** (white-label hosted, simple economic model) |
| **Mid-size enterprise tech-friendly + sovereignty** | **C** (self-hosted runtime) |
| **Mid-size enterprise tech-friendly + zero infra** | **B** (hosted managed) |
| **Financial flow / unbounded cost-of-failure** | **A** (deterministic preferred, regardless of size) |
| **Low-stakes internal automation for your client** | **B** or **C** depending on the client's sovereignty preference |
| **Project without real intelligence required** | **D** (no AI, no complexity) |

## External integration pattern (orthogonal to patterns A/B/C)

For each service connected by the agents (Google, Notion, an internal ERP, an accounting/payment API…), choose ONE integration pattern among 3:

### Pattern 1 — Direct API/token (default to prefer)

**When**: public service with a documented REST API + simple auth (OAuth, API key)

**Examples**: Google APIs, Notion, Slack, Stripe, common accounting/payment APIs…

**Custom MCP server vs CLI helper**: for common services, creating a **Node CLI helper** in `<harness>/scripts/<service>.mjs` is often simpler and lighter than a custom MCP server.

### Pattern 2 — Anthropic MCP Tunnel

**When**:
- Internal corporate service **not publicly exposed** (custom ERP, internal database, internal RBAC)
- Compliance forbids exposure (banking, healthcare, gov)
- You want hosted agents to access MCP servers on YOUR side without exposing them publicly

**How**:
- Lightweight gateway in your network
- Outbound encrypted connection to the provider's routing
- TLS termination on your side (the proxy does not see the payloads)

### Pattern 3 — CLI wrapper for SDK-less services

**When**: site/API **without an official SDK** (legitimate scraping of a site that has no API, etc.)

**How**:
- Reverse engineer the site via Claude Code
- Generate a CLI + MCP server + Claude Code skill

⚠️ **TOS vigilance**: many sites forbid scraping. Check ToS before prod.

### Combinations

| Combo | When to use it |
|---|---|
| **CLI wrapper + MCP Tunnel** | Generate an MCP server for a custom service + host it on your side + expose it to hosted agents via tunnel |
| **Direct API + local cache** | Reduce latency/cost of frequently queried public APIs |
| **Custom MCP server + Tunnel** | If you code an in-house MCP server for an internal service, the tunnel exposes it to hosted agents |

### Integration anti-patterns

- ❌ MCP Tunnel for a public service (= direct API is enough)
- ❌ A CLI wrapper for a service that has an official SDK
- ❌ All-MCP out of dogmatism (MCP is not mandatory)

## Application in Phase 1 Framing (doctrine 12)

### For the `business-analyst`

During interactive discovery, **always ask these 5 questions**:

1. **Cost-of-failure**: *"If the agent makes a mistake on the main action, what is the damage? Reversible / costly but bounded / unbounded (security vuln, SSN leak, lost financial flow)?"*

2. **Critical dev speed**: *"How much time do you have to deliver? Fast MVP or durable product?"*

3. **Acceptable vendor-lock**: *"Are you OK being locked into Anthropic forever, or do you want to be able to swap providers?"*

4. **Tolerable ongoing costs**: *"How much can you afford to spend per month on compute? Does the client pay or you? Variable tokens or fixed compute preferred?"*

5. **Data sovereignty required**: *"Can the data transit through US servers (Anthropic) or must it stay EU/on-prem (strict GDPR, gov, banking, healthcare)?"*

Document the answers in the PRD section "Business need".

### For the `architecte`

Synthesize the BA's answers into an **explicit comparative table** of the 4 patterns in `docs/architecture.md`. Minimum format:

```markdown

|---|---|

| Critical dev speed | yes / no |

|---|---|---|---|---|---|---|
| A deterministic custom | ✅/❌ | ✅/❌ | ✅ | ✅ | ✅/⚠️ | SELECTED/REJECTED |
| B hosted managed | ✅/❌ | ✅ | ❌/✅ | ⚠️ | ⚠️/❌ | SELECTED/REJECTED |

| D pure custom | ❌ (if AI required) | N/A | ✅ | ✅ | ✅ | SELECTED/REJECTED |

### Selected pattern: [A/B/C/D]

[Text synthesis explaining WHY this pattern + WHY the 3 others were rejected]

### External integration patterns per service

| Connected service | Integration pattern | Justification |
|---|---|---|
| Public SaaS API | Direct API (OAuth token) | Documented public API |
| Internal service X | MCP Tunnel | Not publicly exposed, compliance |
```

### For the `reviewer-prd`

In Phase 2 PRD Validation (R001), verify that:
- The "Agent delivery architecture choice" section is present in `docs/architecture.md`
- The 4-pattern comparative table is present
- An explicit verdict for each pattern (SELECTED/REJECTED)
- A non-trivial text justification (not just "no" but "no because…")
- Integration patterns documented per service

If criteria are missing → **PRD NOT OK**, return to framing.

## Anti-patterns to avoid

- ❌ *"We go with deterministic custom by default"* without having considered B/C
- ❌ *"Hosted runtimes are too hype, we avoid them"* without factual justification against the criteria
- ❌ *"We'll see later"* for the external integration pattern (wanting to choose at build time = too late)
- ❌ Adding the comparative table just for show without real reflection (sign: criteria copy-pasted without detail)
- ❌ Choosing a pattern out of dogmatism ("always custom", "always hosted") without context
- ❌ Not distinguishing the architecture pattern (A/B/C/D) from the integration pattern (API/MCP/CLI wrapper) — these are 2 orthogonal axes

## Future evolution of this frame

This frame 14 is **living**. To be updated when:

- A new runtime platform emerges — add it to the evaluated patterns
- A new integration pattern emerges (e.g. a new MCP standard, a new scraping service)
- Empirical feedback from a delivered project changes the reading of the criteria (e.g. cost-of-failure poorly evaluated, to recalibrate)
- Hosted-runtime pricing changes significantly (re-evaluate pattern B vs C)

Versioning:
- **v1.0**: initial creation
- **future v1.x**: append new patterns or recalibrate the matrix
